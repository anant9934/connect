# Connect Database Security Model & Least-Privilege Architecture

## 1. Role Provisioning & Hierarchy
PostgreSQL enforces a strict division between administrative/migration roles and application runtime execution:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        ROLE SEPARATION                                 │
├───────────────────┬────────────────────────────────────────────────────┤
│ Role              │ Privileges & Constraints                           │
├───────────────────┼────────────────────────────────────────────────────┤
│ Migration Admin   │ CREATEROLE, table owner, runs migrations.          │
│ (e.g. postgres)   │ Not used for web request handling.                 │
├───────────────────┼────────────────────────────────────────────────────┤
│ connect_app       │ LOGIN, NOSUPERUSER, NOCREATEDB, NOBYPASSRLS.       │
│                   │ Runtime application role executing web/API queries.│
├───────────────────┼────────────────────────────────────────────────────┤
│ connect_worker    │ LOGIN, NOSUPERUSER, NOCREATEDB, NOBYPASSRLS.       │
│                   │ Dedicated background outbox queue worker role.     │
├───────────────────┼────────────────────────────────────────────────────┤
│ PUBLIC            │ Blanket REVOKE on connect_auth schema and tables.  │
└───────────────────┴────────────────────────────────────────────────────┘
```

## 2. Cryptographic Transaction-Bound Context
Instead of relying on trusted client parameters, Connect uses an HMAC-SHA256 signature generated by `connect_auth.authenticate_session` and verified on every query via Row-Level Security:

$$\text{Signature} = \text{HMAC-SHA256}(\text{Secret}, \text{UserID} \parallel \text{OrgID} \parallel \text{IsSuper} \parallel \text{Role} \parallel \text{Nonce} \parallel \text{XID} \parallel \text{Exp})$$

### 2.1 Cryptographic Context Variables
- `app._user_id`: Authenticated user UUID.
- `app._org_id`: Validated active organization UUID (or empty string for personal workspace).
- `app._role`: Authenticated institutional role (`institution_admin`, `department_coordinator`, `faculty`, `student`, `institution_member`, `institution_auditor`).
- `app._is_super`: Boolean flag indicating platform super-admin status.
- `app._nonce`: 16-byte random hex nonce preventing replay within transaction reuse windows.
- `app._xid`: Current PostgreSQL 64-bit transaction ID (`pg_current_xact_id()`).
- `app._exp`: Unix epoch expiration timestamp (10-minute window).
- `app._sig`: Hex-encoded HMAC-SHA256 signature.

### 2.2 Constant-Time Signature Comparison
All verification procedures utilize `connect_auth.constant_time_equals(a, b)`:
- Computes bitwise XOR across byte sequences.
- Strictly executes in linear time proportional to string length.
- Eliminates timing side-channel leakage.

## 3. Schema & Key Table Isolation
- `connect_auth.internal_keys`: Stores the 256-bit cryptographic key seeded via `public.gen_random_bytes(32)`.
- Explicit `REVOKE ALL ON TABLE connect_auth.internal_keys FROM PUBLIC, connect_app, connect_worker;`.
- Only `SECURITY DEFINER` routines inside `connect_auth` can access `internal_keys`.
- All `SECURITY DEFINER` functions explicitly specify `SET search_path = pg_catalog, public, connect_auth` to prevent search path hijacking.
